**Gewähltes Pattern:** Agent-Team
**Begründung:** Sieben Cross-Layer-Tasks (Build-Tool, Tailwind, Router, i18n, API-Client, PWA, Tests) mit gegenseitigen Abhängigkeiten (Router braucht Layout, Layout braucht Theme, Theme braucht Tokens, Tests brauchen alle). Linear hintereinander abarbeiten.
**Team-Komposition:** Lead (Sonnet/Opus) für Orchestrierung. Pure-Code-Tasks ohne externe Recherche, daher kein Explore-Agent nötig.

## Why

`frontend/src/` ist leer. Bevor ELE-180 (Wochenplan-Grid) starten kann, muss das komplette Frontend-Gerüst stehen: Build-Tool, Styling, Theme-System, Router, i18n, API-Client, PWA-Hülle, Auth-Context-Stub, Layout-Shells (Desktop + Mobile), Test-Konfiguration. Kein Business-Code, kein Login-Form, kein Wochenplan — reines Scaffolding.

Eliminiert die Sprint-1-Lesson "ELE-180 als Wochenplan-Grid hätte de facto 3× mehr Aufwand bedeutet als geschnitten".

## What

Frontend-Workspace `frontend/` produktiv lauffähig:

- `npm run dev` startet Vite-Devserver (`localhost:5173`), proxied auf Backend (`localhost:3000`)
- Layout-Shell mit Sidebar (Desktop) / Bottom-Tabs (Mobile)
- Genau **eine** Route: `/health` mit Backend-Connection-Smoke
- Theme-Switch via `data-tenant`-Attribut (nur Gepard mit Hypothesen-Werten gefüllt)
- Locale-Switch zwischen `en` und `de` via i18next
- JWT-Stub liest aus localStorage, 401 redirected auf Placeholder

## Zusammenfassung

Vorher war das Frontend-Verzeichnis im Repo leer: `frontend/package.json` und ein paar Test-Setup-Stubs, aber keine Zeile App-Code. Die letzten 5 Backend-Issues haben eine vollständige API geschaffen, aber niemand konnte sie im Browser sehen. Hätten wir mit dem nächsten Frontend-Feature (Wochenplan-Grid, ELE-180) direkt losgelegt, hätte das Issue de facto drei Issues in einem werden müssen — Build-Setup + Layout-Gerüst + das Grid selbst. Genau diese Falle hat Sprint 1 in der Learning-Loop dokumentiert.

ELE-199 hat genau dieses Gerüst sauber gebaut, ohne Business-Logik anzufassen. Konkret: **Vite 5 + React 18 + TypeScript-strict** mit Path-Alias, **Tailwind 3.4** das seine Werte aus CSS-Variablen zieht statt sie hartzucodieren, ein **Tenant-Theme-System** über `<html data-tenant="...">` mit drei vorgesehenen Theme-Files (Gepard aktiv, Immobilienbutler + Paul scaffolded), ein **React-Router-Setup** mit einem Desktop-Layout (Sidebar 240px + 5 Nav-Items) und einem Mobile-Layout (Top-Header + Bottom-Tabs), die per Media-Query (768px) automatisch umschalten, **i18next** mit 6 Namespaces in zwei Sprachen mit Locale-Resolution-Chain (JWT-Claim → Browser → Fallback en), einen **fetch-basierten API-Client** der den JWT als Authorization-Header anhängt, die Backend-Locale via Accept-Language mitschickt, und Errors zu strukturierten `ApiRequestError`-Objekten normalisiert (mit `code` und `messageKey` aus dem Backend, was die i18n-Strategie ADR-16 end-to-end durchzieht), ein **PWA-Setup** mit Manifest und Workbox-Service-Worker (NetworkFirst für API-Calls mit 5s-Timeout, Cache für statische Assets), eine **`HealthPage` als Smoke-Route** die direkt den Backend-Status zeigt, und **self-hosted Inter + JetBrains Mono** via `@fontsource` weil Google-Fonts-CDN ein DSGVO-Problem wäre.

Verifiziert ist das Ganze durch **17 Vitest-Smokes** (Layout-Rendering inkl. beider Layouts, Theme-Switch via `data-tenant`-Attribut, JWT-Decode-Edge-Cases, API-Client mit JWT-Header-Injection, Error-Normalisierung, 401-Cleanup, POST-Body-Serialisierung) und **3 Playwright-E2E-Smokes** (App-Boot, Locale-Switch en→de, Login-Placeholder-Route). Der Production-Build ist **285 KB JS / gzip 91 KB**, deutlich unter dem Performance-Budget aus ADR-14 von 250 KB gzip. Alle Type-Checks (Backend + Frontend + E2E) clean, alle Governance-Hooks grün.

**Damit sind ELE-180 (Wochenplan-Grid), ELE-181 (Drag&Drop), ELE-182 (Mobile-PWA-Detail) und ELE-195 (i18n-Frontend) jetzt unblocked.** Robert und Daniel haben noch nichts zu sehen außer einer Status-Seite, aber das nächste Issue kann sich ausschließlich auf das Wochenplan-Grid konzentrieren.
