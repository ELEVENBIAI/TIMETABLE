# Reassignment-Engine — Regelbasiertes Scoring für Vertretungsvorschläge

> **Issue:** ELE-196 | **Erstellt:** 2026-05-16 | **Status:** In Progress
> **Erbe von:** TT-21

## Agent-Pattern

- [x] **Solo** — Backend-only (Frontend-Picker explizit deferred). Pure-Function + Service + Endpoint + Tests. ~6-8h.

**Gewähltes Pattern:** Solo
**Begründung:** Klare Schichtung (pure → service → route), kein Cross-Layer-Aufwand weil Frontend separate Story ist. Test-lastig, aber alles in einem Modul-Tree.

## Why

Krankmeldung → Absence-Logik (ELE-186) markiert betroffene Entries als `REASSIGNMENT_NEEDED`. Heute geht Robert manuell die Liste durch und entscheidet anhand Bauchgefühl + Telefonat. Die Engine soll für jeden markierten Entry eine deterministische, sortierte Top-N-Vorschlagsliste mit Score und i18n-Begründung liefern — in Millisekunden, ohne LLM, ohne Wartezeit.

## What

Backend-Service + Pure-Scoring-Function + `GET /api/schedule-entries/:id/reassignment-suggestions` + Tests. **Frontend-Picker = separates Folge-Issue** (Welle 3).

### Faktor-Mapping (basierend auf ADR-19 + DB-Realität)

ADR-19 nennt 5 Faktoren mit Gewichten 30/25/20/15/10 (Summe 100) und Equipment als Hard-Filter. Die DB hat aber **kein Level-Feld** an `qualification_types` (siehe Migration 0002 — nur `code`/`name`/`requires_proof`). Wir liefern daher Qualifikation pragmatisch als:

| Faktor                | Gewicht | DB-Quelle                                                                      | Skalierung 0-100                                                                 |
| --------------------- | ------- | ------------------------------------------------------------------------------ | -------------------------------------------------------------------------------- |
| **Kapazität**         | 30      | `employees.weekly_hours` (Soll) vs Σ `schedule_entries.duration_min` der Woche | `100 × (1 − geplant/soll)` clamped 0..100; bei `weekly_hours=NULL`: 50 (neutral) |
| **Nähe**              | 25      | Haversine zwischen `employees.home_lat/lng` und `properties.lat/lng`           | `100 × (1 − clamp(km/MAX_USEFUL_KM, 0, 1))`; bei null lat/lng: 50 (neutral)      |
| **Qualifikation**     | 20      | Anzahl gültiger `employee_qualifications` des Mitarbeiters                     | `min(count/3, 1) × 100` — Sättigung bei 3 Qualifikationen                        |
| **Erfahrung**         | 15      | Count `schedule_entries` desselben Mitarbeiters am selben Property in 6 Mon    | `min(count/EXPERIENCE_SATURATION_MONTHS, 1) × 100` (Sättigung wie ADR)           |
| **Fairness**          | 10      | Count `reassignment_log` mit `assigned_employee_id` in FAIR_LOOKBACK_WEEKS     | `100 × (1 − clamp(count/MAX_FAIR_VERTRETUNGEN, 0, 1))`                           |
| **Contingency-Bonus** | bis +10 | `contingency_rules` matchend (employee × property × service_type)              | Bei Match: + (11 − priority) Punkte; final cap auf 100                           |

### Hard-Filter (Kandidat fliegt aus Top-N, taucht aber im `blockers`-Feld auf)

- `is_active=false` oder `is_deleted=true`
- `absence_records` an dem Tag (Type SICK/VACATION/PERSONAL/TRAINING/OTHER)
- Anderer `schedule_entry` zur überlappenden Zeit (Time-Conflict via Inline-Helper)
- `employee.id === entry.employee_id` (kein Self-Reassignment)

### Output

```ts
interface Suggestion {
  employeeId: string;
  employeeName: string; // first_name + last_name
  score: number; // 0..100, gerundet auf 1 Nachkommastelle
  factorScores: {
    capacity: number;
    proximity: number;
    qualification: number;
    experience: number;
    fairness: number;
    contingencyBonus: number;
  };
  reasonKeys: Array<{ key: string; vars?: Record<string, unknown> }>;
  blockerKeys: Array<{ key: string; vars?: Record<string, unknown> }>;
}

interface ReassignmentResponse {
  entryId: string;
  suggestions: Suggestion[]; // Top-N (MAX_SUGGESTIONS), nur unblocked, score >= MIN_SCORE_TO_SUGGEST
  blocked: Suggestion[]; // Hard-gefilterte Kandidaten (für UI-Transparenz)
}
```

`reasonKeys` und `blockerKeys` sind i18n-Keys (ADR-16). Beispiele:

- `reassignment.reasons.capacityHigh` `{ hoursFree: 18 }`
- `reassignment.reasons.proximityNear` `{ km: 2 }`
- `reassignment.reasons.qualificationsCount` `{ count: 3 }`
- `reassignment.reasons.experienceVisits` `{ visits: 8 }`
- `reassignment.reasons.contingencyMatch` `{ priority: 1 }`
- `reassignment.blockers.hasAbsence` `{ absenceType: 'SICK' }`
- `reassignment.blockers.timeConflict` `{ startTime: '08:00' }`
- `reassignment.blockers.selfReassignment`
- `reassignment.blockers.inactive`

## Constraints

### Must

- **Pure Function** in `reassignment-pure.ts` — kein DB-Zugriff, deterministisch, voll unit-testbar
- 5 Soft-Faktoren + 1 Contingency-Bonus (siehe Tabelle oben)
- Hard-Filter mit klaren `blockerKeys`
- Top-`MAX_SUGGESTIONS` aus `REASSIGNMENT_SCORING` (default 3)
- Score unter `MIN_SCORE_TO_SUGGEST` (40) → nicht in Top-N
- i18n-Keys via ADR-16
- Auth: ADMIN/PLANNER/FOREMAN
- Tenant-Scoping bei allen Queries
- TypeScript strict, Zod-Schema für Response
- Coverage Pure-Function ≥ 90%

### Must Not

- Kein LLM-Call (ADR-04)
- Keine automatische Zuweisung
- Kein Schema-Change (alle Tabellen existieren)
- Kein `reassignment_log`-INSERT (das macht Frontend beim "Annehmen")
- Keine Frontend-Änderungen

### Out of Scope

- Frontend-Picker
- `reassignment_log`-Schreiben beim Annehmen
- A/B-Test-Framework
- Tenant-Override der Gewichte
- ML-Tuning

## Tasks

### T1: Pure Scoring-Function

`backend/src/services/scheduling/reassignment-pure.ts`:

- `haversineKm(lat1, lng1, lat2, lng2)`
- `scoreCapacity(plannedMin, weeklyHoursTarget)` → 0..100
- `scoreProximity(km, maxUsefulKm)` → 0..100
- `scoreQualification(qualCount)` → 0..100
- `scoreExperience(visits, saturationMonths)` → 0..100
- `scoreFairness(reassignmentsInWindow, maxFair)` → 0..100
- `applyContingencyBonus(score, priority?)` → 0..100
- `scoreCandidate(input): Suggestion`
- `hardFilters(candidate, entry): blockerKeys[]` (returns array, empty = no block)

**Verify:** ≥24 Unit-Tests in `tests/services/reassignment-pure.test.ts`, alle pure (kein DB).

### T2: Engine-Service (DB-Loader)

`backend/src/services/scheduling/reassignment-engine.ts`:

- `loadEntryContext(pool, tenantId, entryId)` — Entry + Property + Service-Type
- `loadCandidatePool(pool, tenantId, exceptEmployeeId)` — alle aktiven Mitarbeiter im Tenant außer dem Ursprung
- `loadCandidateData(pool, tenantId, employeeId, entry)` — Auslastung, Qualifikationen, Erfahrung, Absence, Time-Conflict, Contingency, Reassignment-Count
- `getSuggestions(pool, tenantId, entryId): Promise<ReassignmentResponse>`
  - Lädt alle Daten **parallel pro Kandidat** (Promise.all)
  - Wendet Pure-Scoring an
  - Sortiert nach Score
  - Splittet Top-N (unblocked, ≥ MIN_SCORE) vs blocked

**Verify:** Service-Integration-Test in `tests/services/reassignment-engine.test.ts` (mit testcontainer + Pilot-Seed).
