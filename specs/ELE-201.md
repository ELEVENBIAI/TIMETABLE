# Backend Auth-Endpoints Ergänzung (forgot-password + GET /me)

> **Issue:** ELE-201 | **Erstellt:** 2026-05-17 | **Status:** Done

## Agent-Pattern

- [x] **Solo** — 2 Routes + Schemas + Tests + Locale-Keys, alles im Backend, klar geschnitten

**Gewähltes Pattern:** Solo
**Begründung:** Zwei kleine Endpoints, klar abgegrenzt. Keine Cross-Layer-Komplexität.
**Team-Komposition:** n/a

## Why

ELE-200 (Frontend Login) braucht zwei Backend-Endpoints, die ELE-170 noch nicht angelegt hat:

- **`POST /api/auth/forgot-password`** — Anti-Enumeration-Stub (immer 200, kein Mail-Send im MVP)
- **`GET /api/users/me`** — Self-Profile-Endpoint für Frontend-Refresh nach Login

Beide klein, gehören zusammen.

## What

- `backend/src/routes/auth.ts` → neue Route `POST /api/auth/forgot-password`
- `backend/src/routes/users.ts` → neue Route `GET /api/users/me`
- Schemas, Locale-Keys, Tests

## Constraints

### Must

- **`POST /api/auth/forgot-password`**:
  - Body: `{ email }` (Zod-validiert)
  - **Immer 200** mit `{ ok: true }` (Anti-Enumeration)
  - Bei existierendem User: Log `action: 'auth.forgot_password_requested', userId, by_ip`
  - Bei unbekannter Email: Log `action: 'auth.forgot_password_unknown_email', emailHash` (kein Klartext)
  - Strengeres Rate-Limit (5/min pro IP) gegen Email-Probing
  - Kein Mail-Versand im MVP (TODO-Comment für Wave 2)
- **`GET /api/users/me`**:
  - Requires Auth (requireAuth preHandler)
  - Returnt aktueller User aus DB via `request.user.userId`
  - Response: `{ id, tenantId, email, displayName, role, isSuperAdmin, locale, mustChangePassword, createdAt }`
  - Soft-deleted User → 401

### Must Not

- Kein echter Mail-Send (Wave 2)
- Keine Password-Reset-Token-Generierung (Wave 2)
- Keine Klartext-Email in Logs (DSGVO)

## Zusammenfassung

Bevor das Frontend einen Login-Button zeigen kann, muss das Backend zwei kleine Funktionen liefern, die im ELE-170-Sprint nicht in Scope waren: einen "Passwort vergessen?"-Endpunkt und eine Möglichkeit, das eigene Profil zu lesen. Beide sind unscheinbar, aber ohne sie würde Frontend-Login-UI gegen ein leeres Loch funken.

Konkret: der **Passwort-vergessen-Endpunkt** nimmt eine Email entgegen und antwortet **immer mit 200**, völlig unabhängig davon ob diese Email im System existiert. Das ist gewollt — wenn das System zwischen "User existiert" und "User existiert nicht" unterscheiden würde, könnte ein Angreifer einfach Email-Listen probieren und herausfinden welche Konten aktiv sind (sogenannte Email-Enumeration). Im Backend-Log wird der existierende User mit seiner ID protokolliert (für späteres Audit), bei unbekannter Email wird nur ein verkürzter SHA-256-Hash der Adresse geschrieben — kein Klartext, DSGVO-konform. Ein verschärfter Rate-Limit (5 Anfragen pro Minute pro IP) verhindert dass jemand das mit Brute-Force probiert. Echte Reset-Mails kommen erst in Welle 2 wenn der Mail-Service integriert wird; der Endpunkt ist also bewusst ein dokumentierter Stub, der bereits den korrekten Anti-Enumeration-Pfad durchläuft.

Der **Self-Profile-Endpunkt** `GET /api/users/me` liefert die aktuellen User-Daten — Anzeigename, Rolle, Locale, ob Passwort-Wechsel ansteht — basierend auf dem User-ID-Claim im JWT, nicht auf einem URL-Parameter. Das verhindert dass jemand mit einem manipulierten JWT andere User auslesen kann. Ist der User in der Zwischenzeit gelöscht worden, gibt der Endpunkt 401 zurück und das Frontend kann den abgelaufenen Token wegwerfen. Damit hat das Frontend nach Login eine zuverlässige Quelle für "wer ist gerade eingeloggt" — ohne das JWT-Payload selbst parsen zu müssen, was bei Locale-Wechseln oder Rolle-Updates durch einen Admin sonst stale Werte zeigen würde.

Beide Endpunkte sind durch 8 Tests abgedeckt (4 für jeden), die jeweils auch die Sicherheits-Eigenschaften explizit verifizieren (identische Response bei bekannten/unbekannten Email, 401 für soft-deleted User, kein PII in Logs). Damit kann ELE-200 mit dem Frontend-Login-Flow starten.
