Vor Pilot-Launch mit Daniel/Anna/Gabi/Jürgen als echte Mitarbeiter müssen DSGVO-Art.-15/17/30-Workflows produktiv sein — Architecture-Review 2026-05-16 hat das als **kritische Lücke** markiert. ## What

Drei DSGVO-Workflows + ein Retention-Cron, Audit-Trail-Frontend, AVV+Datenschutzerklärung-Vorlagen.

### Backend (4 neue Routes unter `/api/dsgvo/*`)

1. **`POST /api/dsgvo/data-export`** — Art. 15 Auskunft
   - Body: `{ employeeId?: uuid }` (default = own employee)
   - ADMIN darf jeden Employee, EMPLOYEE nur sich selbst
   - Liefert ZIP mit `data.json` (vollständig) + `report.md` (lesbar)
   - Aggregation: users, employees, employee_skills, schedule_entries, time_logs (wenn Tabelle existiert), absences, audit_log
   - Schreibt `dsgvo.export` in audit_log

2. **`POST /api/dsgvo/delete-request`** — Art. 17 Löschung (Phase 1: Soft)
   - Body: `{ userId: uuid, reason: string }`
   - ADMIN für andere User, EMPLOYEE für sich selbst (mit `confirmEmail`-Match)
   - Setzt `is_deleted=true` auf: users, employees, employee_skills, schedule_entries (zukünftige), time_logs (jünger 90 Tage)
   - Historische schedule_entries (≥90 Tage) bleiben mit anonymisiertem `first_name='[gelöscht]'`, `last_name=''`
   - Markiert User für Hard-Delete in 30 Tagen via neuer Spalte `hard_delete_at TIMESTAMPTZ`
   - Schreibt `dsgvo.delete_requested` in audit_log

3. **`GET /api/dsgvo/audit-log`** — Art. 30 Auswertung
   - Query: `?userId=&action=&targetType=&dateFrom=&dateTo=&page=&limit=`
   - ADMIN/SUPER_ADMIN only
   - Pagination (default 50, max 200)
   - Format-Switch `?format=csv` für Export

4. **Retention-Cron** — `backend/scripts/dsgvo-retention.mjs`
   - Liest `lib/config.js DSGVO_RETENTION` (Sektion neu)
   - Phase 2 Hard-Delete: User mit `hard_delete_at < NOW()` → PHYSICAL DELETE (außer audit_log)
   - GPS-Felder in `schedule_entries.actual_lat/lng` (falls existiert) → NULL nach `GPS_DATA_DAYS`
   - audit_log älter als `AUDIT_LOG_DAYS` → DELETE (Compliance: 5 Jahre)
   - CLI-Flags `--dry-run` / `--apply`, schreibt Report nach stdout + audit_log-Summary-Eintrag

### Frontend (2 neue Settings-Pages)

5. **`/settings/audit-trail`** — Audit-Trail-Liste (ADMIN/SUPER_ADMIN)
   - Tabelle: created_at, user (resolved), action, target_type, target_id, metadata
   - Filter: action, dateFrom, dateTo
   - "CSV exportieren"-Button → `/api/dsgvo/audit-log?format=csv`
   - Pagination

6. **`/settings/data-export`** — Self-Service-Export für jeden eingeloggten User
   - Button "Meine Daten exportieren" → ZIP-Download
   - Hinweis-Text mit DSGVO-Bezug

### Docs (Pflicht für Pilot-Start)

7. **`docs/dsgvo/datenschutzerklaerung.md`** — generische DE-Datenschutzerklärung-Vorlage
   - Verantwortlicher (Tenant-Brand Placeholder)
   - Verarbeitete Daten + Zweck + Rechtsgrundlage
   - Aufbewahrungsfristen (aus DSGVO_RETENTION)
   - Rechte (Art. 15/16/17/18/20/21)
   - Kontakt (DSB-Platzhalter)

8. **`docs/dsgvo/avv/`** — Auftragsverarbeitungs-Verträge-Templates

## Constraints

### Must

- ADR-07 Soft-Delete-Pattern + ADR-15 audit_log Append-Only respektieren
- `audit_log` darf **niemals** durch DSGVO-Löschung berührt werden (HGB-/DSGVO-Aufbewahrungspflicht)
- Tenant-Scoping bei allen Endpoints
- Self-Service-Löschung erfordert `confirmEmail === user.email` (Phishing-Schutz)
- Hard-Delete-Cron ist **separates Script** (kein Web-Endpoint) — wird via Cron oder GitHub Action getriggert
- Frontend nutzt bestehende auth.tsx + i18n-Pattern (neuer Namespace `dsgvo`)
- Alle 4 DSGVO-Endpoints schreiben audit_log
- TypeScript strict, kein `any`

### Must Not

- Keine harten Lösch-Buttons im UI — Self-Service-Löschung erfordert Bestätigung via E-Mail-Tipp
- Kein direktes audit_log-DELETE aus der App-Rolle (DB-GRANT verbietet das ohnehin)
- Keine ZIP-Streams ohne tenant_id-Check
- Keine PII (Klar-Email/Name/Adresse) in `request.log.info` Logging — nur IDs

### Out of Scope

- DPIA (Data Protection Impact Assessment) — organisatorisches Issue
- DSGVO-Schulung End-User (organisatorisch)
- ML-Anonymisierungs-Algorithmen
- Verschlüsselung "at rest" auf Disk-Level (Hosting-Decision, ELE-191)
- Echte AVV-Verträge unterschrieben (das macht der Operator mit den Providern)

## Zusammenfassung

**Was war das Problem?** Sobald Daniel, Anna, Gabi und Jürgen mit ihren echten Namen, Adressen und Telefonnummern im System arbeiten, fällt das System unter die DSGVO — die EU-Datenschutzgrundverordnung. Ohne konkrete Workflows für "Welche Daten habt ihr über mich?" (Auskunft), "Bitte alles löschen" (Recht auf Vergessenwerden) und "Wer hat wann was angesehen?" (Audit-Trail) wäre der Pilot legal nicht startbar — Bußgelder bis 20 Mio € oder 4% des Jahresumsatzes. Bisher gab es zwar die Datenbank-Strukturen (audit_log-Tabelle existierte), aber keine Endpoints, keine UI, keine Workflows die ein Mitarbeiter oder Admin tatsächlich auslösen kann.

**Was wurde gebaut?** Drei vollständige Workflows:

1. **"Meine Daten herunterladen" (Art. 15):** Jeder eingeloggte Mitarbeiter findet unter Einstellungen → "Meine Daten" einen Button, der innerhalb von Sekunden ein ZIP herunterlädt. Drin: ein technisches `data.json` (alle Datensätze die das System über die Person hat — Account, Mitarbeiter-Profil, Qualifikationen, Arbeitsplan, Abwesenheiten, Audit-Spuren) und ein lesbares `report.md` für die Person selbst. Admins können das auch für andere User auslösen.

2. **"Bitte löschen" (Art. 17):** Phase 1 ist sofortig — beim Klicken werden Account, Mitarbeiter-Profil und zukünftige Aufgaben als "gelöscht" markiert. Historische Aufgaben aus der Vergangenheit bleiben anonymisiert erhalten (HGB-Aufbewahrungspflicht für Geschäftsunterlagen). Phase 2 läuft 30 Tage später automatisch durch einen nächtlichen Skript (Retention-Cron): er löscht den Account physisch und ersetzt alle Personenangaben im Mitarbeiter-Datensatz durch "[gelöscht]". Das Audit-Log bleibt erhalten — wer den Account jemals angeschaut hat, ist nachvollziehbar (anonymisiert über die ID-Ruine). Phishing-Schutz: Für Self-Service muss der Mitarbeiter seine eigene E-Mail-Adresse zur Bestätigung eintippen.

3. **"Wer hat was wann gesehen?" (Art. 30):** Admins finden unter Einstellungen → "Audit-Trail" eine Tabelle mit allen protokollierten Aktionen im Mandanten. Filter nach Aktion (z.B. nur "Mitarbeiter angesehen") oder Datum, Pagination, und ein CSV-Export-Button für Behörden-Anfragen oder interne Reviews.

Dazu kommen drei Dokumente: eine **Datenschutzerklärungs-Vorlage** auf Deutsch mit klar markierten Platzhaltern für Firmenname, DSB-Kontakt usw. (der Anwalt füllt das aus), und **AVV-Templates** (Auftragsverarbeitungsverträge) für OpenRouteService und den Hosting-Provider — beide Pflicht-Verträge nach Art. 28 DSGVO.

**Was ändert sich dadurch?** Der Pilot ist jetzt legal startbar. Wenn die Aufsichtsbehörde anklopft oder ein Mitarbeiter "möchte alles wissen / alles weg" sagt, gibt es einen klar dokumentierten Ablauf mit Audit-Spur. Konkrete Aufbewahrungsfristen sind in `lib/config.js DSGVO_RETENTION` konfiguriert (Mitarbeiterdaten 30 Tage nach Soft-Delete, Zeiterfassung-Logs 1 Jahr, GPS 90 Tage, Audit-Log 5 Jahre) und der Cron läuft idempotent — egal ob einmal pro Tag oder dreimal, das Ergebnis ist gleich. Was noch fehlt für die volle Produktion: echte AVV-Unterschriften (Operator + Anwalt), eine offizielle DPIA (organisatorisch, kein Code), und der Versand einer Bestätigungs-Mail vor dem Hard-Delete (kommt mit dem Mail-Provider-Setup in einem Folge-Issue). Aber die Pflicht-Hürde "Pre-Pilot DSGVO-Lücke" ist genommen.
