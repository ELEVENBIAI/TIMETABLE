# Backend-Skeleton — Fastify + TypeScript + Auth + Swagger

> **Issue:** ELE-169 | **Erstellt:** 2026-05-16 | **Status:** Done | **Abgeschlossen:** 2026-05-16

## Zusammenfassung

**Was war das Problem?** Bis jetzt war die Datenbank zwar produktiv, aber ohne Zugang von außen. Es gab keine Möglichkeit, sich anzumelden, keine API für andere Programme, keine Dokumentation der Schnittstelle. Ohne diesen "Anschluss" könnten weder das Frontend noch externe Tools mit den Daten arbeiten — und ohne Login-Mechanismus auch niemand wissen, wer welche Daten sehen darf.

**Was wurde gebaut?** Ein vollständiges Backend-Skelett mit Fastify (einem schnellen Node.js-Web-Server). Es bietet drei Funktionen: einen Health-Check der prüft ob das System funktioniert, einen Login mit Email und Passwort der einen Sicherheits-Token (JWT) ausgibt, und eine automatisch generierte API-Dokumentation. Der Login ist gegen die häufigsten Angriffe geschützt: Wer 5x das falsche Passwort eingibt, wird 15 Minuten gesperrt. Auch wenn ein Angreifer probiert ob eine bestimmte Email-Adresse existiert (User-Enumeration), bekommt er keine Antwort — wir prüfen jedes Passwort gleich lang, egal ob der Nutzer existiert oder nicht. Alle Aktionen werden strukturiert geloggt (mit Request-ID, Mandanten-ID, User-ID), aber niemals Passwörter oder Tokens — und Email-Adressen werden in den Logs maskiert.

**Was ändert sich?** Ab jetzt kann sich Robert (oder das Frontend) tatsächlich mit der App verbinden. Wir können den Browser auf `http://localhost:3000/api/docs` öffnen und sehen die vollständige API-Doku. Mit dem ausgestellten JWT können wir später Daten abfragen — der Token enthält automatisch Mandant + Rolle + User-ID, sodass die Row-Level-Security richtig filtert. Und das Fundament ist gelegt: Die nächsten Issues (ELE-170 Users-CRUD, ELE-171 Service-Types, etc.) können diese Auth-Middleware einfach nutzen und müssen nicht selbst Login-Logik bauen.

## Why

Grundgerüst für alle weiteren API-Endpoints. Auth + Multi-Tenant-Context muss von Anfang stehen — sonst funktioniert RLS nicht und alle nachfolgenden Issues bauen auf falschen Annahmen.

## What

Fastify 5+ Backend mit TypeScript, zwei DB-Pools (owner/app), JWT-Auth-Middleware, `withTenant()`-Helper, Swagger/OpenAPI, CORS, Rate-Limiting, Zod-Validation-Helper, Pino-Logger, strukturierte Error-Responses.

## Constraints

### Must

- Fastify 5+ mit `@fastify/cors`, `@fastify/rate-limit`, `@fastify/swagger`, `@fastify/swagger-ui`, `@fastify/jwt`, `@fastify/sensible`
- Zwei Connection-Pools: `ownerPool` (für Migrations/Admin), `appPool` (alle API-Requests, RLS erzwungen via `set_config('app.current_tenant_id', …, false)`)
- `withTenant(tenantId, fn)` Helper im Backend (analog `tests/helpers/withTestTenant.ts`)
- JWT-Middleware: Token validieren, `{userId, tenantId, role, isSuperAdmin}` extrahieren, in `request.user` setzen
- Login-Endpoint mit bcryptjs cost 12 (Login-Logik inkl. FAILED_LOGIN_COUNT + LOCKED_UNTIL nach 5 Fehlversuchen für 15 Min)
- **Timing-Attack-Schutz:** bcrypt-Compare auch bei nicht-existentem User (gegen User-Enum-Attacks)
- Rate-Limit: 200 req/min global, 10 req/min auf `/api/auth/*`
- Health-Check `/api/health` → `{ status, db, version }`
- Swagger UI unter `/api/docs`
- `tsconfig.json` mit `strict: true`
- JWT_SECRET aus `.env`, mind. 64 Zeichen, Server startet nicht ohne
- **Pino-Logging (ADR-15):** Pflicht-Felder requestId, tenantId, userId, route, duration, status
- **PII-Sanitization (ADR-15):** kein password/token in Logs, Sanitize-Helper für Error-Logs
- **Performance (ADR-14):** Request-Timeout 10s via `@fastify/sensible`, Pino-`duration` pro Request
- **Feature-Flags (ADR-12):** `FEATURES`-Sektion in `lib/config.js` + `GET /api/config` (whitelisted Subset)
- **Graceful Degradation (ADR-12):** Health-Endpoint liefert 503 bei DB-Ausfall

### Must Not

- Kein eigenes Auth-Library — Standard `@fastify/jwt`
- Keine CRUD-Endpoints (kommen in ELE-170+)

### Out of Scope

- Refresh-Token-Rotation (Welle 3+)
- Passwort-Reset-Flow (Welle 3+)
