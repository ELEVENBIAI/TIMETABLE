# Reassignment-Picker — Frontend-Modal für Vertretungsvorschläge

> **Issue:** ELE-203 | **Erstellt:** 2026-05-17 | **Abgeschlossen:** 2026-05-17 | **Status:** Done
> **Folge von:** ELE-196 ✅ (Backend-Engine + API)

## Agent-Pattern

- [x] **Solo** — Frontend-only. Hook + Modal-Komponente + SchedulePage-Integration + Tests. ~3-4h.

**Gewähltes Pattern:** Solo
**Begründung:** Eine Modal-Komponente, ein TanStack-Query-Hook, ein Trigger-Button im Grid. Kein Cross-Layer (Backend steht).

## Why

ELE-196 liefert das Engine-Backend, aber unsichtbar. Robert kann die Vorschläge nicht im UI sehen — Engine ist "wirkungslos" ohne Picker. Dieses Issue baut das letzte Stück damit der komplette Krankheits-Fall mit zwei Klicks geht.

## What

Frontend-Modal + Integration in SchedulePage:

1. **Trigger**: ScheduleEntryCard mit `status='REASSIGNMENT_NEEDED'` zeigt UserPlus-Icon-Button "Vertretung finden" (nur sichtbar für ADMIN/PLANNER/FOREMAN — EMPLOYEE sieht es nicht).
2. **Modal** `ReassignmentPickerModal.tsx`:
   - Header: "Vertretung für [Property-Name] am [Datum]"
   - Top-N Suggestions als Karten mit Score-Badge + Faktor-Breakdown + Reason-Tags
   - Ausklappbare Liste der Blocked-Kandidaten mit Begründung
   - Klick auf Kandidat-Karte → ruft `useMoveScheduleEntry({ employeeId })` → Modal schließt → Erfolgs-Toast
3. **TanStack-Query-Hook** `useReassignmentSuggestions(entryId)`:
   - GET `/api/schedule-entries/:id/reassignment-suggestions`
   - 30s `staleTime`
   - `enabled` nur wenn Modal offen
4. **i18n-Namespace `reassignment`** im Frontend (en + de — Strings aus Backend-Locales mirrored)

## Constraints

### Must

- Trigger-Button nur für `ADMIN`/`PLANNER`/`FOREMAN` sichtbar (Role-Check via `useAuth`)
- `useReassignmentSuggestions` via TanStack-Query (`staleTime: 30_000`, `enabled` gesteuert)
- Reason-Strings via `t(key, vars)` über `reassignment`-Namespace
- Modal `role="dialog"`, ESC schließt, Click außerhalb schließt
- Auswahl löst `useMoveScheduleEntry({ id, scheduleId, employeeId })` aus (bestehender Endpoint ELE-181, der `is_from_reassignment=true` setzt)
- Erfolgs-Toast oder Inline-Bestätigung
- TypeScript strict
- A11y: Fokus-Trap im Modal, Close-Button mit aria-label

### Must Not

- Kein neuer Backend-Endpoint
- Keine direkte `reassignment_log`-Schreibung im Frontend
- Kein DnD-Trigger (Modal kommt über expliziten Button, nicht durch Drag)
- Kein Schema-Change

### Out of Scope

- `reassignment_log.was_accepted`-Feedback-Loop — separates Issue (Wave-3-Polish)
- A/B-Test-Framework
- Mehrfach-Selektion / Bulk-Reassignment
- Filter/Search im Modal (Top-N ist bereits sortiert + gefiltert)

## Zusammenfassung

**Was war das Problem?** Die Backend-Engine aus ELE-196 lieferte zwar perfekte Vertretungsvorschläge mit Score und Begründung — aber Robert konnte sie nicht sehen. Im UI gab es keinen Knopf, kein Modal, nichts. Wer als Admin den API-Endpoint aufrufen wollte, brauchte einen JWT-Token und `curl`. Praktisch nutzlos für den eigentlichen Anwender.

**Was wurde gebaut?** Ein **Picker-Modal**, das direkt im Wochenplan-Grid erscheint. Wenn eine Aufgabe als `REASSIGNMENT_NEEDED` markiert ist (z.B. weil der Mitarbeiter krankgemeldet wurde), zeigt die Card jetzt einen kleinen Button "Vertretung finden" — aber nur, wenn der eingeloggte User ADMIN, PLANNER oder FOREMAN ist (Mitarbeiter sehen das nicht). Klick öffnet ein Modal mit Header ("Vertretung für Porzer Str. 12, Mi 20.05, 08:00"), darunter Top-3 Kandidaten als anklickbare Karten — jede mit großem Score-Badge (farbig: grün ≥70, gelb ≥50, rot darunter), Faktor-Breakdown (Kap 80 · Näh 95 · Qual 67 · ...), und einer Liste lokalisierter Begründungen ("Wohnt nur 2 km entfernt", "Hat noch ~18h frei diese Woche"). Darunter ein ausklappbarer Bereich "Nicht verfügbar (2)" — wer geht nicht, warum (Krankmeldung, Terminkonflikt, etc.). Klick auf einen Kandidaten weist die Aufgabe sofort um (über den bestehenden Move-Endpoint aus ELE-181, der nebenbei `is_from_reassignment=TRUE` setzt) und das Modal schließt sich. ESC oder Klick außerhalb schließen ohne Aktion. Die Reason-/Blocker-Texte kommen vom Backend als Strings mit Variables (z.B. `{ key: 'reassignment.reasons.proximityNear', vars: { km: 2 } }`) und werden im Frontend lokalisiert gerendert — auf Englisch oder Deutsch je nach Sprach-Einstellung.

**Was ändert sich dadurch?** Wave 3 ist als sichtbares Feature komplett. Der ursprüngliche User-Story-Wunsch — "Daniel ruft krank an, Robert hat in 2 Klicks die Vertretung organisiert" — funktioniert jetzt End-to-End. Robert sieht im Wochenplan die rote Aufgabe, klickt "Vertretung finden", wählt Anna (Score 78, beste Kandidatin), fertig. Vorher: 45 Minuten Telefonate + Excel-Check. Jetzt: 2 Klicks. Was noch fehlt für die volle Schleife: das automatische **Logging** in `reassignment_log` mit `was_accepted=true` — der Move passiert bereits, aber das Log-Event ist noch nicht spezifisch markiert (kann als Polish-Issue ergänzt werden, sobald wir die Acceptance-Rate-KPI aus ADR-19 messen wollen).
