# JWT-Secret-Rotation-Strategie (Pre-Pilot)

> **Issue:** ELE-188 | **Erstellt:** 2026-05-17 | **Abgeschlossen:** 2026-05-17 | **Status:** Done

## Agent-Pattern

- [x] **Solo** — Backend Multi-Secret-Support + Rotation-Script + ADR + Doku.

**Gewähltes Pattern:** Solo
**Begründung:** Klar abgegrenzt, ~2-3h, keine Cross-Layer-Recherche.

## Why

Bei JWT-Secret-Leak gibt es aktuell **kein dokumentiertes Verfahren**. `signJwt`/`verifyJwt` lesen `process.env.JWT_SECRET` — wenn der kompromittiert ist, gibt es nur die Brechstange: alle User sofort ausloggen (Total-Logout, alle Sessions weg, schlechte UX). Vor Pilot mit echten Mitarbeitern muss eine **planmäßige Rotation** und ein **Notfall-Playbook** stehen. Architecture-Review 2026-05-16 hat das als Tech-Debt-Punkt A markiert.

## What

**ADR-18 + Multi-Secret-Verify + Rotation-Skript + Operator-Playbook.**

> Hinweis Nummerierung: Issue-Beschreibung sagt "ADR-16", aber ADR-16 ist bereits i18n-Strategy und ADR-17 ist ELE-189 Error-Tracking. Wir nutzen **ADR-18**.

Konkretes Deliverable:

1. **ADR-18 `docs/ADR-18-jwt-secret-rotation.md`** — Multi-Secret-Strategie + Rotation-Playbook
2. **Backend** akzeptiert beim Verify zwei Secrets:
   - `JWT_SECRET` = primary (Sign + Verify)
   - `JWT_SECRET_PREVIOUS` = nur Verify (Übergangszeit ~7 Tage)
   - Verify-Logik: erst primary, bei Fehler vorheriger
   - Sign nutzt **immer** nur primary
3. **Rotation-Script** `scripts/rotate-jwt-secret.mjs`:
   - `--dry-run` zeigt Plan ohne Änderung
   - `--apply` ersetzt `.env`:
     - Backup `.env` → `.env.<timestamp>.bak`
     - Schreibt `JWT_SECRET_PREVIOUS=<alter Wert>`
     - Generiert neues `JWT_SECRET` (48 Bytes via `crypto.randomBytes(48).toString('base64')`)
   - Hinweis im Output: "Restart backend, dann nach 7 Tagen JWT_SECRET_PREVIOUS entfernen"
4. **Operator-Playbook** in `GOVERNANCE.md` Sektion "JWT-Secret-Rotation":
   - Geplante Rotation (alle 90 Tage)
   - Notfall-Rotation bei Verdacht (sofort)
   - Cleanup nach 7 Tagen
5. **Tests** Vitest: signJwt mit primary, verifyJwt mit primary, verifyJwt mit previous (= rotation simuliert), verifyJwt fail bei drittem Secret

## Constraints

### Must

- `signJwt` nutzt **immer** das primary Secret — niemals previous
- `verifyJwt` versucht primary zuerst, dann previous
- Beide Secrets müssen `SECURITY.JWT_SECRET_MIN_LENGTH` (64 chars) erfüllen
- Rotation-Script ist **idempotent**: zweimal `--apply` rotiert zweimal (kein "rotiert schon vor 10 Sekunden")
- `.env`-Backup vor jeder Rotation
- TypeScript strict, kein `any`
- Tests funktionieren in CI (kein Secret-Leak in Logs)

### Must Not

- Keine automatische Rotation per Cron (Out of Scope, manuell reicht für Pilot)
- Kein HSM/Vault (Out of Scope, Welle 6+)
- Keine Änderung am JWT-Payload-Format
- Kein Secret im Git committen

### Out of Scope

- Automatische Rotation per Cron
- HSM / Vault-Integration
- Forced-Logout-Endpoint — Operator-Playbook gibt eine SQL-Variante ("update users set must_change_password=true") als manuelle Notbremse

## Zusammenfassung

**Was war das Problem?** Wenn das geheime Passwort, mit dem die Login-Tokens (JWT) signiert werden, jemals nach außen leakt — z.B. weil ein Backup verloren geht, ein Mitarbeiter es versehentlich in einen Chat kopiert, oder ein Server kompromittiert wird — kann ein Angreifer **beliebige Tokens fälschen** und sich als beliebiger User ausgeben. Bisher gab es nur eine einzige Notbremse: das Secret ändern. Aber dann werden in derselben Sekunde alle gerade eingeloggten User rausgeworfen — Robert mitten in der Planung, Daniel mitten in der Mobile-Ansicht. Schlechte UX und Anfälligkeit für Fehler ("haben wir nach dem letzten Leak schon rotiert? Wann nochmal?").

**Was wurde gebaut?** Eine **doppelte Schloss-Strategie**: Das System hat jetzt zwei "Schlüssel" gleichzeitig — einen aktuellen (`JWT_SECRET`) und optional einen vorherigen (`JWT_SECRET_PREVIOUS`). Neue Login-Tokens werden immer mit dem aktuellen Schlüssel signiert. Beim Prüfen eines bestehenden Tokens probiert das System zuerst den aktuellen, und falls das fehlschlägt, den vorherigen. Praktisch: Wenn der Operator den Schlüssel rotiert (egal ob planmäßig alle drei Monate oder im Notfall bei Verdacht), bleiben alle gerade eingeloggten User **drin** — ihre alten Tokens funktionieren noch über den "vorherigen Schlüssel". Erst nach sieben Tagen (Tokens laufen ohnehin nach 7 Tagen ab) entfernt der Operator den vorherigen Schlüssel manuell, und alles ist wieder im "Single-Lock"-Zustand. Die Rotation selbst ist ein einziger Befehl: `node scripts/rotate-jwt-secret.mjs --apply` — das Skript macht ein Backup der `.env`, generiert ein neues Geheimnis mit 64 Zeichen, schiebt das alte in `JWT_SECRET_PREVIOUS` und schreibt zurück. Im Operator-Handbuch (GOVERNANCE.md) stehen drei klare Szenarien: planmäßige Rotation alle 90 Tage, Notfall-Rotation (zusätzlich SQL-Befehl der alle User zum Passwort-Wechsel zwingt), und das Cleanup nach 7 Tagen.

**Was ändert sich dadurch?** Der Operator hat jetzt ein **dokumentiertes, geübtes Verfahren** für eine Situation die irgendwann auftreten wird (jedes Secret muss irgendwann rotiert werden — IT-Security-Best-Practice). Keine Panik, keine User-Disruption, kein "wie war das nochmal?". Das ist der dritte und letzte Baustein im Pre-Pilot-Sicherheits-Pflicht-Block: zusammen mit DSGVO-Workflows (ELE-187) und Error-Tracking (ELE-189) ist die Plattform jetzt rechtlich und operativ pilot-bereit. Bleibt nur noch die Hosting-Entscheidung (ELE-191), dann kann Robert den Pilot starten.
