## Agent-Pattern

- [x] **Solo** — Frontend-only, ein Modal + Hook + zwei Trigger.

**Gewähltes Pattern:** Solo
**Begründung:** Klein, frontend-only, ~2-3h.

## Why

Backend kann seit ELE-186 Absencen verarbeiten + Schedule-Entries automatisch markieren. Aber das Frontend hat keinen Trigger dafür. Robert kann den ELE-203-Picker ohne SQL-Eingriff nicht testen, und in Production muss er sowieso Krankmeldungen erfassen können.

## What

Modal `ReportAbsenceModal.tsx` mit Variante-C: 2 Trigger.

1. **Global**: Button im SchedulePage-Header — Mitarbeiter wählbar im Modal
2. **Kontextuell**: Pro Mitarbeiter in `WorkloadSummary` — Mitarbeiter preselected

Modal-Form-Felder:

| Feld        | Required | UI                                  |
| ----------- | -------- | ----------------------------------- |
| employeeId  | ✓        | Select (nur wenn nicht preselected) |
| absenceType | ✓        | Select (5 Typen)                    |
| startDate   | ✓        | date-Input, default heute           |
| endDate     | ✓        | date-Input, default = startDate     |
| notes       | optional | textarea (max 2000)                 |

Submit → POST `/api/absences` → invalidate `scheduleKeys.entries(scheduleId)` → Cards werden rot.

## Constraints

### Must

- AbsenceTypes: SICK / VACATION / PERSONAL / TRAINING / OTHER
- Default-Datum: heute (Von + Bis)
- Validation: `startDate <= endDate` clientseitig + servervalidiert
- TanStack-Query-Mutation, `useReportAbsence()`
- Erfolg → Modal schließen + Toast oder Inline-Confirm
- Auth-Gate für Trigger: ADMIN/PLANNER/FOREMAN nur
- i18n (en + de) — neuer Namespace `absences`
- A11y: role=dialog, ESC, Backdrop-Click, autoFocus auf erstem Feld
- TypeScript strict

### Must Not

- Kein neuer Backend-Endpoint
- Keine Bulk-Eingabe
- Keine Edit/Delete-Workflows
- Keine direkten Schedule-Updates im Frontend (Backend macht das)

### Out of Scope

- Liste der bestehenden Absences (eigenes Folge-Issue)
- Self-Service-Sick-Report für EMPLOYEE (eigenes Folge-Issue, Backend unterstützt's bereits)
- Drag-Datum-Picker (Range-Picker)
- Halbtags-Granularität (`isFullDay=false` + startTime/endTime)

## Zusammenfassung

**Was war das Problem?** Robert konnte das schöne neue ELE-203-Modal ("Vertretung finden") gar nicht testen oder benutzen — denn dafür müsste eine Aufgabe im Wochenplan den Status `REASSIGNMENT_NEEDED` haben. Das passiert im echten Leben automatisch wenn ein Mitarbeiter sich krank meldet (Backend-Logik aus ELE-186 markiert dann alle betroffenen Aufgaben). Aber: es gab im Frontend **keinen Knopf** um diese Krankmeldung einzutragen. Robert musste in der Browser-Konsole `fetch()`-Aufrufe machen — als Operator unbenutzbar.

**Was wurde gebaut?** Ein **Krankmelden-Modal** mit zwei Triggern, je nach Situation:

1. **Globaler Trigger** im Wochenplan-Header (neben "Plan freigeben"): Button "Abwesenheit melden" — öffnet ein leeres Modal, wo Robert den betroffenen Mitarbeiter aus einer Liste wählt.
2. **Kontextueller Trigger** in der Auslastungs-Übersicht unten: Bei jedem Mitarbeiter steht ein kleines Symbol "Krankmelden" — Klick öffnet das gleiche Modal, aber mit dem Mitarbeiter bereits vorausgewählt.

Das Modal enthält dann: Mitarbeiter (Dropdown oder fix), Abwesenheits-Art (Krankheit / Urlaub / Persönlich / Schulung / Sonstiges), Von-Datum, Bis-Datum, optional eine Notiz. Default sind Von/Bis auf heute gesetzt, Art ist "Krankheit". Ein Klick auf "Abwesenheit speichern" schickt das ans Backend (`POST /api/absences`), das vorhandene Backend-Logik aus ELE-186 schreibt einen Abwesenheits-Record und markiert **automatisch alle Aufgaben** des Mitarbeiters in diesem Zeitraum als `REASSIGNMENT_NEEDED`. Im Frontend wird der Schedule-Query invalidiert → Wochenplan rendert sofort neu → die betroffenen Karten erscheinen mit roter Markierung + dem "Vertretung finden"-Button. Ein Klick darauf öffnet das ELE-203-Modal → Robert wählt eine Vertretung → fertig.

**Was ändert sich dadurch?** Wave 3 ist jetzt **end-to-end durchklickbar im UI** — keine SQL-Konsole, keine fetch-Hacks. Der komplette Krankheits-Workflow vom Anruf bis zur fertigen Umverteilung läuft in unter einer Minute: Daniel ruft an, Robert klickt 2× ("Krankmelden" → Daniel auswählen → Speichern) und sieht alle roten Karten der Woche. Dann pro Karte 1× ("Vertretung finden" → Anna auswählen) — fertig. Was hier bewusst nicht drin ist (eigene Folge-Issues, falls gewünscht): eine **Liste der erfassten Absences** zum Editieren/Löschen, **Self-Service** für Mitarbeiter (Daniel meldet sich selbst krank — Backend kann's bereits, UI fehlt), **Halbtags-Granularität** (start_time/end_time), **Range-Date-Picker** statt zwei Inputs.
