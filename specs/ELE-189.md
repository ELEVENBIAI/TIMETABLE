## Why

Im Pilot brauchen wir Sichtbarkeit auf 500-Errors ohne dass Robert oder Daniel anrufen müssen. Aktuell gehen Pino-Logs auf stdout — kein zentraler Sammler, kein Dedup, kein Alarm bei Spikes. Architecture-Review 2026-05-16 hat das als Tech-Debt-Punkt B markiert. Vor Pilot-Start brauchen wir mindestens eine **Sentry-API-kompatible** Anbindung im Code, auch wenn der konkrete Server (GlitchTip-Instanz) erst mit dem Hosting-Setup live geht.

## What

**ADR-17 + Sentry-SDK-Wire-Up (Backend + Frontend) + Setup-Doku.**

Konkretes Deliverable:

1. **ADR-17 `docs/ADR-17-error-tracking.md`** — Provider-Entscheidung: **GlitchTip** als Primär (selfhosted, AVV-frei, DSGVO-konform, Sentry-API-kompatibel). Sentry SaaS als dokumentierte Backup-Option mit AVV-Auflage.
2. **Backend-Integration `@sentry/node`**:
   - `backend/src/lib/tracking.ts` — Init wenn `SENTRY_DSN` gesetzt, sonst no-op
   - `app.ts setErrorHandler` ruft `captureException()` nur für 5xx (4xx ist Client-Fehler, nicht relevant)
   - PII-Scrubbing: keine Bodies, keine Header außer `user-agent`, kein Klartext-Authorization
3. **Frontend-Integration `@sentry/react`**:
   - `frontend/src/lib/tracking.ts` — Init wenn `VITE_SENTRY_DSN` gesetzt
   - `<ErrorBoundary>` um App-Tree mit Fallback-UI
   - Tenant-Context wird gesetzt (tenantId, role — keine PII)
4. **Source-Maps**: `@sentry/vite-plugin` conditional aktiviert wenn `SENTRY_AUTH_TOKEN+ORG+PROJECT` gesetzt — sonst skipped (Dev-Build bleibt schnell)
5. **5xx-Spike-Alert**: in ADR dokumentiert als GlitchTip-/Sentry-UI-Konfiguration (kann nicht im Code gesetzt werden — das ist Server-Side-Setup)
6. **Setup-Doku** `docs/ERROR_TRACKING.md` — wie spinne ich GlitchTip lokal via Docker auf, wo finde ich Errors, wie konfiguriere ich Alerts

## Constraints

### Must

- Code läuft auch **ohne** DSN (Dev-Default = kein Tracking, no-op)
- 4xx Errors **nicht** an Tracking-Service (zu viel Noise, keine Bugs)
- PII-Scrubbing: kein Authorization-Header, kein JSON-Body mit Klartext-Daten
- `lib/config.js`-SSoT respektieren — kein Hardcoding
- TypeScript strict, kein `any`

### Must Not

- Keine produktive Anbindung an externen Sentry-SaaS ohne AVV — DSN bleibt Operator-Aufgabe nach Hosting-Decision
- Keine PII (Klar-Email, IP, Adresse) in `captureException` extra payload
- Kein automatisches Senden in Tests (DSN explizit aus)

### Out of Scope

- Performance-Monitoring (Tracing) — kommt mit Grafana-Stack Wave 4
- User-Feedback-Widget
- Konkretes GlitchTip-Deployment (kommt mit ELE-191 Hosting-Decision)
- Tatsächliche Alert-Channels (Telegram-Bot, E-Mail-Smtp) — Server-Side-Config bei GlitchTip

## Zusammenfassung

**Was war das Problem?** Wenn im Pilot etwas schiefgeht — ein 500-Fehler im Backend, ein React-Crash im Frontend — bekommt das aktuell niemand mit. Die Logs verschwinden im stdout des Servers (oder in der Browser-Console des Users), bis Robert oder Daniel anruft. Kein Stacktrace-Dedup ("derselbe Fehler ist gerade 50× passiert"), kein Alarm wenn die Fehlerrate plötzlich hochschnellt, kein zentraler Ort wo der Operator nachschauen kann was im letzten Monat schiefging.

**Was wurde gebaut?** Die App ist jetzt **"Sentry-ready"** — sowohl Backend als auch Frontend können ihre Fehler an einen zentralen Sammel-Server schicken, der sie aufbereitet, dedupliziert und durchsuchbar macht. Welcher Server das ist, kann der Operator selbst entscheiden:

- **GlitchTip** (empfohlen): läuft auf eigenem Server, ist Open-Source und gratis, datenschutzfreundlich (kein US-Anbieter).
- **Sentry SaaS** (Alternative): Industrie-Standard, viel Komfort, aber USA-Server und kostenpflichtig ab 5.000 Fehlern/Monat.

Beide sprechen das gleiche Protokoll — der Wechsel zwischen ihnen ist nur ein DSN-Tausch, kein Code-Change. Aktuell ist im Code alles vorbereitet, aber **noch kein Server angebunden**: Wenn `SENTRY_DSN` in der `.env` leer ist, läuft die App komplett wie vorher, kein Tracking, kein zusätzlicher Netzwerk-Verkehr. Sobald der Operator nach der Hosting-Entscheidung (ELE-191) eine GlitchTip-Instanz aufsetzt und die DSN einträgt, fließen Fehler dort hin. Im Browser fängt ein **AppErrorBoundary** zusätzlich React-Render-Crashes auf — der User sieht statt einer weißen Seite ein "Etwas ist schiefgelaufen — Seite neu laden"-Dialog, und der Fehler wird im Hintergrund gemeldet. Source-Maps lädt die CI auf Wunsch hoch, sodass Stacktraces lesbar bleiben (nicht nur minifizierte Funktionsnamen). Wichtig: **keine personenbezogenen Daten** (E-Mails, Adressen, JWT-Tokens) werden mitgesendet — das filtert das System im `beforeSend`-Hook automatisch raus.

**Was ändert sich dadurch?** Der Operator hat jetzt das Werkzeug, um den Pilot ernsthaft zu betreiben: Wenn um 03:00 nachts ein neuer Bug auftritt, kommt morgens ein Webhook auf sein Handy ("10+ Fehler in 5 Minuten"), er öffnet die GlitchTip-UI, sieht Stacktrace + Häufigkeit + betroffene User + Tenant, und kann reagieren ohne dass Robert ihn anrufen muss. Das ist der Unterschied zwischen "Hobbyprojekt" und "lauffähiger Pilot". Was noch fehlt für Production: der GlitchTip-Server muss tatsächlich aufgesetzt werden — das kommt mit ELE-191 (Hosting-Decision). Bis dahin: der Code ist drin, getestet, und wartet auf seine DSN.
